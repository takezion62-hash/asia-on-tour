# 長期運用 第5段階：main書き込み競合対策

## 変更

mainへ直接pushする5つのActions（直近戦績、過去戦績、参加記録、本番再生成、過去大会カレンダー）を既存グループ `aot-provider-results-main` へ統一し、`queue: max`、`cancel-in-progress: false` を設定。1つのグループで同時に実行されるワークフローは1つ。GitHub公式の複数待機機能で最大100件の待機を保持する（上限超過やキャンセル等はあり得る）。従来の1待機枠による置き換えを避け、異なる種類のスキャンを同時に走らせない。

公式仕様：https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency

## 安全性と範囲

- 定期実行cron、push対象パス、API予算、公開データ、承認ルールは変更しない。ワークフロー追加なし。
- 既存の最新mainへの再適用、検証、非force pushは維持する。人間のPRマージ、外部push、移行前の実行済みワークフローとは競合し得る。
- カレンダーだけに不足していたpush再試行（最大5回）を追加。最新mainの変更がカレンダーの入力・既存アーカイブに影響する場合は安全停止し、再調査が必要。競合を無理に解決しない。再base後も検証する。
- レビュー用のPR作成ワークフローはmainへ直接書き込まないため、別グループを維持。テスト・Pagesデプロイも変更しない。
- キューはワークフロー全体を直列化するため、調査開始や再生成の待ち時間が増える可能性がある。上限超過時はキャンセルされ得る。実運用で待機時間・キャンセル・競合失敗・再試行回数を確認する。今回の変更で完全な無競合やAPI使用量の低下を保証しない。

## 検証

`node --test tests/main-writer-queue.test.cjs` で直接main writerの一覧、同一グループ、待機保持、元のcron、既存の再試行、非force push、カレンダーの入力ガードと再検証の順序を保護する。既存PRの全テスト・本番再生成隔離リハーサルも実行する。実際のGitHubキュー挙動はマージ後に確認する。
