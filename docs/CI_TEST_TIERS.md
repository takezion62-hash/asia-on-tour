# CI運用：3段階テストとPR分割（2026-11-15）

ASIA ON TOURでは、変更内容のリスクごとに必要なテストを実行する。テスト成功は登録成績の正しさの唯一の証拠ではなく、出典の照合・本人Epic ID確認・手動承認は引き続き必要。

## 1. 成績登録・選手名義の更新 → data（軽量）

- 原則：**データファイルだけ**を変更するPR。 `source-results/Sxx.json` と `source-results/manifest.json` を両方更新する。
- `players.json`、`approval-history.json`、`updates.json`、`season-data/*`、確認待ち索引等の許可された差分を含められる。
- 例：既存名義を別名に紐付けた上で、過去成績を同一選手へ改名するときは、全該当シーズンの正本シャードとmanifest、生成済み索引を同じデータ専用PRで更新する。
- 例外：結果ファイルに変更が**一切ない**純粋な別名義追加は、以下すべてを満たす場合のみ data とする。
  - 信頼できるmain側の `players.json` とPR側を比較可能。
  - `candidates` は完全一致。既存別名の削除・変更・並べ替えをしない。
  - 既存の正規名はそのまま。新しい別名だけ追加し、別の正規名・別名と競合しない。
  - 許可変更ファイルは `players.json`、`season-data/*`、`candidate-triage.json` のみ。
  - 候補を確認した根拠（EpicアカウントID、Trackerリンクなど）はPRに明記する。CIの名前衝突チェックだけで本人を確認した扱いにしない。
- **必須**：全データ/賞金/本人ID/重複検証、正本シャードのチェックサム、公開索引の完全一致、関連データ回帰テスト、PC・スマホのスモーク検証。
- 検証に失敗したデータ専用PRはマージしない。

## 2. 本人ID照合・賞金判定などの**局所コード**修正 → focused

- 原則：**コードと専用テストのみ**のPRを先に作成する。成績の正本ファイルは変更しない。
- 既知の `scripts/validate-approvals.cjs`、専用 `scripts/apply-*.cjs`・`scripts/verified-*.cjs`（対応するテストが存在する場合）、限定されたUI変更が対象。
- **必須**：共通データ/賞金/本人ID/大会/承認検証、関連単体テスト、変更した公開画面があればPC・スマホの両方を検証。適用用スクリプトにはdry-run検証を行う。
- 新しい個別大会の公開処理が必要なら、このコードPRで検証処理を先にマージ。続いて登録データだけのPRを出す。
- 対応テストが見つからない場合、未許可のファイルを変更した場合は **full** に戻す。検証コードを修正して判定範囲を拡張するときも、初回は full で確認する。

## 3. 共通処理・CIルール変更・不明な影響 → full

- 例：`scripts/source-results-store.cjs`、`scripts/data-checks.cjs`、`scripts/ci-change-scope.cjs`、`app.js`全体、CIワークフローの規則変更、非許可ファイル、削除や不正な差分。
- `source-results` と実行可能な検証コードを**同じPR**で変える場合も、フルテストを維持する。安全性のため、混合PRを自動的に軽量化しない。
- 既存の全単体テスト、過去大会dry-run、PC/スマホの全ブラウザテストを実施。
- 毎日 **午前3時（日本時間）** の全検証は、この分類とは別に維持する。

## 実際の進め方

1. 画像やEpic IDに矛盾があれば、まずコードだけのPRを作って関連テストで修正を確認する。
2. コードPRのマージを確認後、最新mainから新しいデータ用ブランチを作る。過去戦績・選手名義・賞金・出典を変更し、生成ファイルを更新する。
3. データ専用PRで軽量CI（unit + PC/mobile smoke）を通し、マージする。
4. どちらかの判定が `full` なら理由をGitHub Actionsの「変更範囲の安全判定」ジョブの概要で確認。データとコードの混在ならPRを分割し直す。未知変更を安全確認抜きで「focused」に指定しない。

GitHubの必須ステータスは従来通り `JSON検証・単体テスト・PCスマホ回帰テスト` を維持。**スキップされた検証を成功扱いにしない。**
