# 長期運用 第3段階：固定反映バッチの再実行削減

第2段階で適用済みと確認した10本・90戦績を対象とする。本番再生成の135個のNodeコマンドを125個にまとめる（内部で実行されるNodeプロセス数とは異なる）。

各ラッパーは従来の dry-run を必ず実行する。成功、追加0、期待件数すべてが既存の正確な証拠と一致、賞金・別名義などの追加なし、レビュー待ちなし、更新マーカー一致、対象実行ファイルのGit blobハッシュ一致の場合に限り2回目の apply を省略する。証拠不足、内容変更、未知の出力では旧applyを実行する。dry-run の失敗はそのまま失敗とする。最後の全データ・承認・更新履歴・索引検証は変更しない。

元の10本、証拠検証、承認・更新履歴、再生成内での実行順序を維持する。未精査67本と継続実行7本の動作を変えない。API呼び出し、公開戦績、選手、賞金、定期自動更新の頻度は変更しない。

隔離コピーの本番再生成リハーサルでは、省略条件を満たした場合も元のapplyを実行し、全ファイル内容のハッシュを実行前後で比較する。差があればPRの統合テストを失敗させる。通常の本番再生成ではこの比較用のapplyを実行しない。比較のためCI自体が速くなるとは限らない。

緊急時は AOT_FORCE_PUBLICATION_REPLAY=1 を設定すれば全対象の旧dry-run + applyへ戻る。対象ファイルを改修した場合も、承認済みのソースハッシュを再確認するまで旧処理へフォールバックする。安全性のため、省略対象の追加は個別レビューと回帰テストが必要。

計測：AOT_FIXED_REPLAY の eligible / skippedApply / verifiedEquivalent で各バッチの判断を確認する。実測の所要時間はマージ後の実行ログと比較し、未測定の短縮率を断定しない。
